# 项目 README · Prompt 设计说明规范

本规定适用于本文件夹下（及后续）每个 Agent / RAG / Tool Calling 相关项目。  
**每个项目的 README 必须包含「Prompt 设计说明」章节**，按下列条目逐项写清，不可省略。

---

## 一、必须说明的内容

### 1. 使用了哪些 Prompt 结构

写明本项目实际采用的结构组合，例如（按实际选用勾选并解释）：

| 结构 | 是否使用 | 说明 |
|------|----------|------|
| System Prompt | 是/否 | 角色、目标、全局约束 |
| User Prompt 模板 | 是/否 | 任务输入如何拼装 |
| 角色设定（Role） | 是/否 | 身份与能力边界 |
| 任务描述（Task） | 是/否 | 本轮要完成什么 |
| 上下文（Context） | 是/否 | RAG 检索结果、历史对话、工具返回等 |
| 输出约束（Format / Schema） | 是/否 | JSON / Markdown / 固定字段 |
| CoT / 思考步骤 | 是/否 | 是否要求分步推理 |
| Tool / Function Calling 指令 | 是/否 | 何时调工具、如何传参 |
| Few-shot 示例 | 是/否 | 见第 3 条 |

要求：不只列名字，需说明**各段在代码/配置中的位置**（文件路径或关键名）。

### 2. 为什么这样设计 System Prompt 和约束条件

必须回答：

- System Prompt 给模型定了什么角色与目标？
- 有哪些硬性约束（禁止事项、必须事项、范围边界）？
- **为什么**这样写（防幻觉、控格式、限工具、对齐业务等）？
- 约束过严/过松时曾出现过什么问题？如何权衡？

### 3. 是否使用 Few-shot 示例

必须明确写：

- **用了 / 没用**
- 若用了：示例条数、示例覆盖什么场景、放在 System 还是 User、为何选这些例子
- 若没用：原因（任务简单、已用 Schema 约束、成本/长度限制等）

### 4. 如何控制输出格式

说明采用的一种或多种手段，例如：

- Prompt 内明确字段名、类型、顺序
- JSON Schema / Pydantic / 结构化输出 API
- 后处理校验（正则、JSON parse、字段白名单）
- 失败重试 / 二次纠正 Prompt

并给出**期望输出样例**（可脱敏）与**校验位置**（代码路径）。

### 5. 如何处理模型不确定、越界回答或格式错误

至少覆盖三类失败，并写清策略：

| 情况 | 检测方式 | 处理策略 |
|------|----------|----------|
| 不确定 / 证据不足 | 如低置信、检索为空、回答含「猜测」 | 拒答、追问、降级回答、标注「无法确认」 |
| 越界回答 | 话题/权限/工具范围外 | 拒绝、重定向到允许范围、不执行危险工具 |
| 格式错误 | 解析失败、缺字段、类型不符 | 重试、纠正 Prompt、回退默认结构、记日志 |

### 6. Prompt 修改前后效果对比（至少 3 组）

用表格记录，每组包含：修改动机、改前 Prompt 要点、改后 Prompt 要点、观察指标/现象。

示例格式：

| # | 修改动机 | 改前表现 | 改后表现 | 结论 |
|---|----------|----------|----------|------|
| 1 | … | … | … | … |
| 2 | … | … | … | … |
| 3 | … | … | … | … |

指标可写：格式合规率、拒答是否合理、工具调用正确率、幻觉次数、人工主观质量等。  
**至少 3 组**；鼓励附上关键 Prompt 片段（可截断）。
